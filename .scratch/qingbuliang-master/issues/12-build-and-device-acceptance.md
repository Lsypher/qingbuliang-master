**发现（按严重程度）**

1. **构建产物带着"丢失脚本"（已修）**：`main.scene` 里其实还挂着一个 `SelfCheck` 组件——它以**压缩 uuid** `aa270V6/l5GxbJD1ywVLLm9` 存储，按名字搜索根本搜不到，所以"删掉 `debug/`"这一步当时并没有真正删干净。删掉脚本后，构建产物一启动就报
   `Error 3817: ... 'Canvas' which with an index of 4 is corrupted! It has been removed.`（引擎把坏组件丢掉）。修法：在编辑器里把组件从 Canvas 摘掉再保存场景（编辑器保存能力本次正常）。
   编辑器保存时又一次把视口状态写回文件（Canvas `_lpos` 80,920、`_contentSize` 160×1840），已按 11 号切片的口径改回设计值（720×1280 @ 360,640），场景 diff 里只剩"删掉那个组件 + `__id__` 顺延"。
   修完复测：产物启动零异常。
2. **窄屏裁切（已修，这是第 10 条的实质内容）**：设计分辨率 720×1280 用 `FitHeight`，在比 9:16 更窄的全面屏手机上（390×844 → **可见宽只有 591 设计像素**）会把两侧切掉：
   - 配料盘四列固定 180 间距（内容宽 700）→ 最外两列的图标与中文标签被切；
   - 开始页"玩法一句话"（642 宽）左右各切 25 px（截图里首字与末字都缺了一半）。
   修法：`IngredientTray` 按 `view.getVisibleSize().width` 均分四列（591 可见宽下格子 160→130、间距 180→140，收窄下限 110），`StartView` 把玩法一句话的盒子收进可见宽度并交给引擎缩字号（`Overflow.SHRINK`，关掉自动换行以保住一行高度）。**宽屏（可见宽 ≥720）行为完全不变**。
   实测（改动后，五视口）：360×740 / 414×896 上格子与文案都落在可见区内（余量 20~37 px）；1280×800 与 768×1024 上仍是设计值（格子 160、文案 642、不缩字号）。
   未动的一处：碗区拖动高亮框 600 宽，在 591 可见宽下左右各出屏约 4.5 px——它比判定区小一圈、又只在下拉时出现，判定区本就比它大，故保留原样；`TrayArea` / `BowlArea` / `StartPage` 的 720 宽面板是**全屏出血的底衬**，出屏是有意为之。
3. **`HudView` 销毁期崩溃（已修）**：编辑器日志里翻到预览停止时 `HudView.stopPulse` 报 `Cannot read properties of null (reading 'setScale')`——组件 `onDestroy` 时子节点已被先一步回收，`label.node` 已是 null。加了一句存在性校验（`node?.isValid`）。产物复测：最后一局归零后立刻刷新页面（此时脉冲仍在跑），控制台**零异常**。
4. **背景素材带水印（已按用户指示裁掉）**：4 张背景图的右下角都有 **"豆包AI生成"** 水印；`palm-coast-dusk.jpg` 还不只是水印——它是一张**手机截图**，顶部带着状态栏（35% 电量、信号、Wi-Fi、电池图标），底部还有 home 指示条。玩游戏时：单局页底部被配料盘盖住看不见，但**开始页与结算页压暗后两者都清晰可见**。已从 `e0ed041` 原图裁切：统一裁下 98 px、左右各 26 px，`palm-coast-dusk` 另裁上 138 px、左右各 65 px。
   这不是代码问题，是素材交付问题（`CREDITS.md` 记的是"按出图需求产出、由用户交付"）。处置建议：**重出**是首选（去掉水印、不要用手机截图当底图）；退而求其次我可以裁掉水印带（底部约 5% 高度，构图基本无损；`palm-coast-dusk` 还要连顶部约 3% 的状态栏一起裁，代价是图源比例从 9:16 略微变宽松，拉伸后肉眼几乎看不出）。**等用户拍板再动**——改的是交付来的美术资源，不擅自改。
5. **favicon 404（未处理）**：构建模板的 `index.html` 没有图标链接，浏览器默认请求 `/favicon.ico` → 控制台一条 404 网络错误。影响仅是控制台噪音；要修得加自定义构建模板，不属本切片。
6. **编辑器噪声**：重开编辑器会把 `settings/v2/packages/information.json` 里 splash 插件的表单状态改掉（`enable` 翻转 + 加 `sid=`），与本项目无关，已丢弃。

## 评审（Standards × Spec 双轴，改动未提交，基准 = HEAD c9e9b17）

**Standards 轴**：

- **违反"禁止重复封装"（已修）**：`Math.min(SCREEN_WIDTH, view.getVisibleSize().width)` 在 `IngredientTray` 与 `StartView` 各写一份、注释也各解释一遍。下沉为 `uiFactory.visibleWidth()`，两处共用；`IngredientTray` 不再直接 import `SCREEN_WIDTH`。
- **收窄不可逆（已修）**：`fitHowToPlay` 收窄过之后就没有回宽屏的路径，窗口拉宽会一直用小字号。改成记住场景里摆的原始宽度、每次按 `min(原始宽度, 可见宽度 - 留白)` 重算：宽屏还原 `Overflow.NONE`，窄屏才 `SHRINK`。
- **只在开局算一次（已修）**：格子尺寸是开局按可见宽度算的，视口一变（转屏 / 工具栏收起 / 拖窄窗口）就不准了。补 `view.on('canvas-resize')` 重排（拖动中先按"被打断"收尾再重建），`StartView` 同样跟着重算。这是第 10 条"元素不被裁切"在运行期的最后一块拼图。
- **文档不实（已修）**：README 原来把"命令行构建、退出码 36 = 成功"写成结论，实则本机命令行方式零产出（见评论开头）。改成"官方文档这样约定 + 本次实测如此"两段分开写。`docs/design/mvp-spec.md` 技术约定里的目录列表还留着 `debug`，已同步。
- **未改（判断）**：新增的 `MIN_SLOT_WIDTH` / `TRAY_SIDE_MARGIN` / `COLUMN_GAP` / `HOW_TO_PLAY_SIDE_MARGIN` 留在组件里没进 `config/`——与既有 `COLUMN_SPACING` / `SLOT_WIDTH` / `SLOT_HEIGHT` 同类，是组件私有排版参数（照 10 号切片"字号属组件私有排版参数"的判例）。
- **未改（判断）**：`usable` 里 `Math.max(…, COLUMN_COUNT * MIN_SLOT_WIDTH)` 这个下限在真实机型（可见宽 ≥570）不会触发，只在把桌面窗口拖成细条时兜底，注释已写明；删掉它反而会在极端窄窗口把格子压到认不出。
